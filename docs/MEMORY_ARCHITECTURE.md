# Agent 记忆架构

记忆与知识库是两套不同的数据面：记忆保存“当前对话和项目中的状态、决策与偏好”，知识库保存“标准、公司模板、领域规则和历史证据”。Agent 先读取与当前项目有关的记忆，再按需调用知识工具，不把完整知识库塞进模型上下文。

## 三层记忆

| 层级 | SQLite 表 | 内容 | 注入策略 |
| --- | --- | --- | --- |
| 短期记忆 | `conversation_messages` | 用户与 Agent 的原始对话轮次、模型和意图元数据 | 每次取当前项目最近 12 条，按时间顺序注入 |
| 工作记忆 | `working_memory` | 当前 Agent 的目标、待补字段、最近意图、输入是否齐全、执行状态 | 按 `project_id + namespace` 读取一个最新快照 |
| 长期记忆 | `long_term_memory` | 已确认的项目决策、用户偏好、企业规则；带来源、置信度和状态 | 只读取 `confirmed` 记录，按项目和 Agent 限定范围 |

权威数据库位于项目根目录的 `data/projects/.workflow.sqlite3`。项目目录中的 `events/conversation.jsonl` 只是便于人工审计和迁移的可读投影，不负责查询和上下文注入。

## 软件接口 Agent 的使用方式

1. 后端从 SQLite 读取最近对话、`software_interface` 工作记忆和已确认长期记忆。
2. 只把自然语言和内存摘要发给 DeepSeek；本地文件路径仍由后端结构化字段持有。
3. 模型返回 `execute`、`answer` 或 `clarify`：
   - `answer`：直接回答业务问题，不运行文件工具。
   - `clarify`：提出一个真正阻塞执行的问题。
   - `execute`：输出受约束的业务操作，再交给确定性工具。
4. 用户明确“修改时间较晚的文件是新版”时，该项目决策进入长期记忆；实际时间比较由后端读取文件元数据确定性完成。
5. 每轮用户消息和 Agent 回复写入 SQLite，同时投影到 JSONL，刷新页面后由 `/api/projects/{project_id}/messages` 恢复。

## 边界

- 不把未经确认的模型猜测自动写入长期记忆。
- 长期记忆按项目和 Agent 隔离，不跨公司项目自动传播。
- 原始文件、标准正文和公司模板不进入记忆表，继续由知识库、RAG 和产物存储管理。
- 工作流执行、租约和审批仍由现有 SQLite 工作流表管理；记忆不会绕过人工门禁。
