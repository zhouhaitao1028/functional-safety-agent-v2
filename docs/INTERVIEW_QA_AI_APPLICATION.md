# AI 应用开发面试问答：FuSa Agent V2

> 适用岗位：AI 应用开发、Agent 应用开发、AI 后端、AI 工程化。  
> 整理日期：2026-11-03。  
> 题目依据：用户提供的抖音作品标题，以及可公开读取的同主题面经文本。回答只使用项目已经实现或验证过的事实；尚未完成的能力单独标注。

## 一、先把项目讲清楚

### 30 秒版本

我在实习中接手了一个面向 ISO 26262 功能安全交付的 Agent 项目。旧方案更像“通用 Agent 加固定目录流程”，任务边界、知识、模板和计算逻辑耦合在一起，执行重、慢，而且难以审计。

我把它重构成了 `Manager 动态路由 + 业务 Engineer Agent + 确定性 Validator + 独立知识平台 + 人工审批门`。Manager 只理解任务和生成 DAG 工作计划；Engineer 负责 HARA、FTA、需求追溯、软件接口分析等具体业务；ASIL 查表、配置对比、追溯完整性等确定性工作由代码执行；知识通过混合 RAG、关系图和 Wiki 独立提供；每个阶段产物都经过 Schema 校验，并用 SHA-256 绑定人工审批。

我还把一个“外部接口生成与对比工具”重构成了软件接口 Engineer，并通过 MCP 暴露三个确定性工具，最后用 FastAPI 做了可视化测试台。真实工具包测试解析了 59 个模块、10,603 条接口记录，审查了 2,639 条跨应用链路，识别出 353 条缺失链路。

### 2 分钟架构版本

一次任务的完整链路是：

```text
用户目标 + 项目输入物
        ↓
Manager 调用 agent_registry.list 和 source.inspect
        ↓
生成结构化 Workplan（Agent、输入输出、依赖 DAG、人工门）
        ↓
Schema + Agent 能力契约 + DAG 数据流校验
        ↓
人工批准计划
        ↓
Workflow 原子领取并行就绪的 Engineer
        ↓
Engineer 按权限调用知识工具 / 项目产物 / 确定性工具
        ↓
确定性校验 + JSON 产物 + provenance + SHA-256
        ↓
人工批准后，下游 Agent 才能消费
```

模型在这个系统里不是最终裁决者。模型负责理解、规划和生成候选内容；程序负责约束、计算和校验；人负责批准。

## 二、按面经问题逐题准备

## 1. 自我介绍时怎么引出这个项目？

### 可直接说

我主要做 AI 应用工程和 Agent 落地，关注的不是简单接一个模型接口，而是怎么把模型放进一个可控、可验证的业务系统。在实习项目里，我负责重构功能安全 Agent：从 Manager 动态路由、业务 Agent 注册、混合 RAG 和图关系，到 Function Calling、MCP、确定性校验、人工审批及 FastAPI 测试台都参与了实现。我比较有代表性的工作，是把原有的软件接口工具改造成可审计的 Engineer Agent，并在真实企业数据上完成端到端验证。

### 面试表达重点

- 不要从“我用了哪个模型”开始讲。
- 先讲业务痛点，再讲架构决策，最后用真实数据闭环。
- 明确自己的贡献：重构架构、实现 Manager、知识工具、软件接口 Agent、MCP 和 Web 测试台。

## 2. 平时如何跟进 AI 前沿技术？

### 可直接说

我把信息源分为四层。第一层是官方文档和协议，例如模型 API、MCP 和主流 Agent SDK；第二层是论文和技术报告，用来判断新方法解决的是什么问题；第三层是开源仓库和 issue，看实际工程限制；第四层是产品实测和面经场景，看能力能否落地。我不会只收藏信息，通常会做一个最小验证，再决定是否进入项目。例如 MCP 我不是只看概念，而是实现了一个 stdio Server，并用真实 JSON-RPC 的 `initialize`、`tools/list` 和 `tools/call` 跑通过。

## 3. 哪门课程对 AI 工程化帮助最大？

### 推荐回答：软件工程

对我帮助最大的是软件工程。AI 应用最大的问题通常不是“模型会不会回答”，而是需求是否明确、模块边界是否稳定、状态能否恢复、结果如何测试和审计。我在项目中把这些思想落实为 Agent Registry、JSON Schema、DAG、接口契约、自动化测试和版本化产物。Prompt 只是实现的一部分，真正让系统可靠的是工程约束。

如果面试官更偏后端，也可以补充操作系统和数据库课程对并发、持久化、事务和资源隔离的帮助。

## 4. 操作系统知识如何用于 Agent 开发？

### 可直接说

Agent 系统本质上也是一个长耗时、I/O 密集、带外部进程和状态的后端系统。操作系统知识主要体现在四点：

1. 并发与阻塞：模型调用、文件解析是阻塞 I/O，FastAPI 中我把耗时操作放进线程池，避免阻塞事件循环。
2. 进程与 IPC：MCP stdio Server 由宿主启动，通过 stdin/stdout 交换 JSON-RPC；协议输出和日志输出必须隔离。
3. 资源边界：工具调用轮数限制为 8，最高 16；文件访问有路径白名单；不执行未知 EXE 和 VBA。
4. 状态持久化：不能把状态只放在模型上下文里，工作计划、产物、审批和事件都落盘，临时文件完成后原子替换。

### 不要过度声称

当前项目还没有做到容器级 CPU/内存配额，也没有分布式任务队列；这是生产化下一阶段，而不是已经实现的能力。

## 5. 除了 AI 项目，还做过传统后端吗？

### 可直接说

这个项目本身也包含完整的后端工程。我用 FastAPI 提供项目、Agent Registry、Manager 规划、审批、Workflow 执行、产物读取和事件审计等 12 组 API；耗时任务进入线程池；领域异常返回结构化错误；数据落在项目级存储中，审批绑定产物哈希。前端是一个轻量单页控制台，可以完整走创建项目、规划、审批、执行和结果审查流程。

如果面试官要求“非 AI 的另一个项目”，需要换成自己的真实经历，不要编造。

## 6. 挑一个最满意的 AI 落地场景，难点是什么？

### 可直接说

我最满意的是软件接口追溯 Agent。输入不是一段文本，而是一个 76MB 左右的企业工具包，包含 59 个 XLSM 模块字典、PIE Matrix、当前和基线配置、已有接口总览以及一个没有源码的旧 GUI 工具。

最大难点不是 Excel 读取，而是怎么划分模型和程序的责任。接口计数、配置差异、链路存在性都必须可重复，所以我用 Python 确定性实现；模型只用于 Manager 路由，不参与这些计算。Agent 输出保留工作簿、Sheet、行号、源指纹和哈希，最后通过人工门确认。

真实运行中解析了 59/59 个模块，提取 10,603 条接口，审查 2,639 条跨应用链路，其中 2,286 条有效、353 条缺失。分析过程约十几秒，但这只是对现有产物的结构化审计，不能宣称完全复刻了旧 EXE 的全部私有生成规则。

### 一个很好的 Bad Case

第一次让 Manager 真正生成计划时，它正确选择了软件接口 Engineer，但又多加了一个当前没有自动执行器的文档 Agent，而且虽然声明依赖上游，却没有把上游输出放进 `input_refs`。

我没有只改 Prompt，而是补了三层机制：

1. Agent Registry 返回 `automatic_executor`，Manager 只能选当前可执行的 Agent；
2. Workplan 契约要求每个依赖必须真实消费上游结构化输出；
3. 后端拒绝无效计划，并把校验错误返回模型自动修正。

这个案例说明 Prompt 优化只是软约束，生产系统必须有后端硬约束和可恢复循环。

## 7. 为什么 RAG 没用 Knowledge Graph？

### 项目的真实回答：我们用了，但没有一开始就上重型 GraphRAG

项目不是“完全没用图”，而是采用混合 RAG 加轻量知识图。当前知识平台索引了 74 份文档、591 个证据块和 390 条关系，检索先做词法与向量融合，再从命中文档扩展“指导手册—模板—业务域”等显式关系。Wiki 和 Agent 检索共用同一个索引。

没有直接上完整 GraphRAG，主要有三个原因：

1. 当前数据规模不大，很多高价值关系本身来自企业流程和模板映射，不需要先做昂贵的社区发现；
2. 功能安全更重证据定位，必须回到文档、段落、表格行和工作表，图摘要不能替代原始证据；
3. 先验证混合召回和显式关系是否有效，再决定是否增加实体抽取、社区摘要和跨文档推理，成本更可控。

### 当前边界

开发环境仍使用离线哈希向量，尚未替换为正式 Embedding，也没有完整的 RAG 离线评测集。因此应该说“图增强检索基础版已实现”，不能说“完整 GraphRAG 已生产化”。

## 8. Token 消耗做过哪些控制？

### 已实现的控制

1. Manager 不读取完整文件，只通过 `source.inspect` 获取受限元数据、后缀统计和少量样例文件名。
2. 知识检索默认最多返回 8 条，后端上限 12 条；图遍历深度默认 1，最高 3。
3. 每个 Agent 只拥有自己的知识标签和工具白名单，避免把整个知识库塞进上下文。
4. 工作项只读取显式 `input_refs` 指向的上游产物，不拼接完整项目历史。
5. 确定性任务不调用模型，例如 ASIL、FTA 最小割集、接口配置对比和追溯校验。
6. Manager 选择最小必要 Agent 集合；工具循环默认最多 8 轮。
7. 输出强制为结构化 JSON，减少解释性废话；完整证据落盘，只把证据 ID 和必要片段放进上下文。
8. 已生成但待审批的工作项不会重复运行。

### 必须诚实说明

项目目前还没有接入各模型的 token usage、费用统计、Prompt Cache 命中率和预算熔断，所以不能编造“成本下降百分之多少”。下一步会记录每轮输入/输出 token、工具结果大小、首 Token 延迟和任务总成本，再做模型路由与缓存优化。

## 9. 自己定义过哪些 Function Calling 工具？

### 可直接说

我定义的工具不是一个万能 Python 执行器，而是按业务语义拆分的只读小工具：

- `agent_registry_list`：返回 Agent 输入、输出、业务能力、人工门和自动执行能力；
- `source_inspect`：检查允许的项目输入，只返回受限文件或 ZIP 元数据；
- `knowledge_retrieve_evidence`：返回带版本、状态和定位信息的证据包；
- `knowledge_graph`：从已经召回的知识节点做受控关系扩展；
- `artifact_list`、`artifact_read`：只允许读取当前工作项声明的项目产物。

软件接口能力还通过 MCP 暴露三个工具：

- `fusa_interface_analyze_package`
- `fusa_interface_compare_configs`
- `fusa_interface_inspect_overview`

每个工具都有 JSON Schema、参数校验和权限边界。模型如果调用未授权工具、错误标签或越权路径，后端会拒绝并把可重试错误作为 tool message 返回。

### Function Calling 与 MCP 的区别

Function Calling 是模型在一次对话中表达“我要调用什么函数及参数”；MCP 是宿主与外部能力之间的标准协议，解决工具发现、跨进程和跨框架复用。项目内部同进程调用直接走 Python 服务以降低开销；外部子 Agent 才通过 MCP 调用同一服务。

## 10. 现在用什么 AI 编程工具？有什么方法？

### 基于真实项目的回答

我主要使用 Codex 辅助代码理解、重构、测试和文档整理。我的原则不是把整个需求一次性扔给模型，而是先写清架构约束和验收标准，再让模型做小范围实现；每次修改后运行真实测试和真实数据链路。

如果被追问 Cursor，而自己没有持续使用，就不要硬说“独家技巧”。可以说方法与工具无关：

1. 用架构文档、Schema、Agent 配置和 Skill 固化长期上下文；
2. 一次只让模型处理一个有边界的改动；
3. 先让模型阅读现有契约和测试，再改代码；
4. 让模型解释 diff 和风险，不以“能运行”作为完成标准；
5. 保留真实 Bad Case 作为回归用例。

## 11. 为什么 AI 生成的代码能跑，但逻辑很差？

### 可直接说

因为“能跑”只说明通过了语法和局部路径，不代表理解了业务不变量。常见原因包括上下文不完整、需求有歧义、模型偏向生成常见模式、缺少负例，以及测试只覆盖 happy path。

这个项目的做法是把业务不变量外置：Agent 的 `consumes/produces`、JSON Schema、DAG、审批门、知识状态和路径权限都由程序校验。比如 Manager 选错文档 Agent 时，Prompt 看起来合理，但后端知道它没有执行器，所以直接拒绝。AI 代码和模型输出都要经过契约、测试、真实数据和人工审核，不能把“模型自信”当正确性。

## 12. AI 编程和 Agent 运行时如何管理上下文？

### 可直接说

我把上下文分成四层，而不是都塞进聊天记录：

1. 长期规范：架构文档、Schema、Agent 配置和 Skill；
2. 全局知识：版本化知识库、原始模板、证据块和图关系；
3. 项目状态：Workplan、已批准产物、审批记录、事件日志；
4. 当前任务上下文：本工作项允许的输入、少量检索证据和工具返回。

模型每次只看到完成当前任务所需的最小上下文。重要状态落盘并有 ID 和哈希，不能只依赖对话窗口。

## 13. Context Window 满了，优先丢弃什么？

### 可直接说

我不会按时间简单截断，而是按“能否重建”和“是否影响决策”分层处理。

优先丢弃或压缩的是重复日志、已经失败且没有新信息的尝试、可以通过 ID 重新读取的原始工具输出、重复召回的证据块和已经用不到的工具定义。

必须保留的是用户目标、当前 Workplan、结构化输入输出契约、已批准产物摘要、未解决问题、关键错误、证据 ID 和决策理由。原始大文件不进上下文，只保留定位信息，需要时再检索。

## 14. 如何看 Spec-driven Development 在 AI 时代的变化？

### 可直接说

AI 时代 Spec 更重要，但形式从一份静态需求文档变成了可执行约束。Prompt 不是完整 Spec；真正的 Spec 应该包括输入输出 Schema、工具权限、状态机、失败策略、验收测试和人工门。

在这个项目里：

- Agent 配置是能力 Spec；
- JSON Schema 是数据 Spec；
- Workplan 是执行 Spec；
- Skill 是操作规范；
- 单元测试和真实数据回归是验收 Spec；
- 审批和 provenance 是治理 Spec。

模型可以根据自然语言生成候选 Spec，但后端必须验证。第一次 Manager 生成错误计划的案例，正好说明“模型生成 Spec + 程序验证 Spec”比只写 Prompt 更可靠。

## 15. 现在 AI Coding 工具最大的瓶颈是什么？

### 可直接说

我认为最大的瓶颈已经不只是代码生成能力，而是长期任务中的意图保持、状态管理和可验证性。模型能快速写出局部代码，但它不天然知道企业业务约束、哪些知识已批准、哪些操作有风险，也不能自己证明结果正确。

所以 Agent 应用的核心竞争力是 Harness：上下文如何组织、工具如何授权、状态如何持久化、错误如何恢复、结果如何评测和审计。FuSa 项目本质上就是在补这一层，而不是再造一个通用 Codex。

## 三、算法题准备

公开文本中还有两道手撕题。这两题不需要硬套项目，但应准备清晰复杂度分析。

### 无重复字符的最长子串

- 方法：滑动窗口 + 字符最后出现位置哈希表。
- 时间复杂度：`O(n)`。
- 空间复杂度：`O(k)`，`k` 为字符集大小。
- 面试注意：左边界只能向右移动，使用 `left = max(left, last[ch] + 1)`。

### 旋转图像

- 方法一：先沿主对角线转置，再反转每一行。
- 时间复杂度：`O(n²)`。
- 额外空间：`O(1)`。
- 面试注意：题目通常要求原地修改，不能另建同规模矩阵。

## 四、面试官很可能继续追问

## 1. 为什么是多 Agent，不是一个强模型？

业务需要不同输入输出契约、知识权限和校验方式。Manager 只规划，Engineer 只做一种业务，Validator 用代码校验。拆分的目的不是模拟组织结构，而是降低权限和上下文范围，让错误可定位。简单任务仍只选一个 Engineer，不会为了多 Agent 而多 Agent。

## 2. 为什么不用 LangChain/LangGraph？

当前核心需求是显式契约、人工门和确定性服务，调度规模较小，所以先用轻量 Python 内核，状态和失败路径更透明，也避免框架升级带来的耦合。不是否定 LangGraph；当需要分布式 checkpoint、并发 Worker、复杂循环和可视化图编排时，可以把现有 Workplan/DAG 迁移过去，因为业务 Agent 和数据契约已经独立。

## 3. 如何评估 Agent 效果？

当前有 28 项自动化测试，覆盖 Schema、DAG、审批失效、知识工具强制调用、工具纠错、确定性计算、并发领取、租约失效、迟到提交拒绝、MCP 路径策略和 FastAPI 路由；另外用真实软件接口包做端到端验证。

但模型规划还没有正式离线评测集。下一步会从真实任务构建“正确 Agent 选择、正确依赖、输入保持、工具调用合规、计划长度、人工修改率”等指标，并保留 Bad Case 回归。

## 4. 如果模型或工具调用失败怎么办？

工具参数错误会作为可重试 tool message 返回模型；工具循环有最大轮数，防止无限 ReAct；Schema 或 Workplan 契约失败会把错误反馈给 Manager 修正；已经落盘的工作项状态不会因对话丢失。

当前模型 API 还缺少指数退避、限流和熔断，这是需要明确补齐的生产化能力。

## 5. 如何保证安全？

- 模型只看到 Agent 配置允许的工具；
- 知识草稿默认不可用；
- 项目产物只能按 `input_refs` 读取；
- MCP 文件路径受允许根目录约束；
- 不提供任意命令执行工具；
- 不执行工具包里的未知 EXE 和 VBA；
- Agent 配置禁止明文密钥字段；
- 模型输出视为不可信候选，必须经过 Schema、代码校验和人工门。

## 6. 多 Agent 如何并行？

Workplan 用 DAG 表达依赖，Workflow 会从 SQLite 状态库原子领取当前就绪节点，并用本地线程池并行执行。每个任务有 worker ID、租约 token、心跳、尝试次数和幂等键；只有批准状态才释放下游，迟到 Worker 不能覆盖新结果。当前边界是单机 Worker Pool，不是多机分布式调度；外部模型调用仍是 at-least-once，不应宣称 exactly-once。

## 7. 这个项目真正的业务价值是什么？

它不是替代功能安全工程师做最终判断，而是把企业已经验证过的流程、模板、证据和确定性规则固化成可复用的工程系统：减少机械解析和追溯工作，提前暴露缺失链路，保存证据来源，并让每一步都可复核、可回退、可审计。
